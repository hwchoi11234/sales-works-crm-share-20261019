# Sales Works CRM · 최종 공유본 (2026-10-19)

프랜차이즈 광고·영업대행 CRM의 별도 공유 저장소입니다. 현재 로컬 작업의 app/components/db/lib 업무 코드와 동일한 버전에서 분리했습니다. 고객 DB 점수 기능이 포함되어 있습니다.

## 바로 실행

Node.js 22.13 이상과 Python 3이 필요합니다. Windows 설치·2주 피드백 서버 절차는 `START_HERE.txt`와 `HANDOFF_FOR_CODEX.md`를 읽으세요.

```sh
npm ci
python3 scripts/restore-handoff.py --verify-only
python3 scripts/restore-handoff.py
npm run dev
```

Windows에서는 `python3` 대신 `py -3`을 사용합니다. 복원은 빈 `.local/development`에만 가능합니다. 기존 DB가 있으면 덮어쓰지 않습니다. 복원 후 `db:setup`·계정 시드를 다시 실행하지 마세요.

접속: http://127.0.0.1:4317 · 데모 관리자: 최고관리자 / 1234

## 공유 범위

- 소스, lockfile, 테스트, Windows 실행 스크립트, 지침, 임시 데이터 374건(브랜드 18개)을 포함합니다.

- 일반 직원/브랜드 테스트 계정과 업무 흐름은 포함된 데모 DB를 기준으로 확인합니다.

- Sites 미리보기 의존성만 제거하고 Windows 환경변수 실행을 Node 래퍼로 전환했습니다. 원본 작업 폴더는 변경하지 않았습니다.
- 다운로드 ZIP에는 빌드 결과 `dist/`가 포함됩니다. Git에는 소스를 추적하며 `npm run build`로 생성합니다.
- Mac에서 타입 검사·주요 단위 테스트·빌드를 확인합니다. 실제 Windows 설치와 외부 네트워크 검증은 대상 PC에서 진행해야 합니다.

# Sales Works · 로컬 개발

하루포케·앙팡프리슈·구천구백닭강정의 가상 고객 30명과 영업팀원 6명으로 사용하는 로컬 CRM입니다. 운영 배포·운영 DB 연결은 차단되어 있습니다. Git 작업이나 원격 저장소 전송 없이 로컬에서만 개발합니다.

## 실행

- 개발: http://127.0.0.1:4317 (`npm run dev`)
- 별도 테스트: http://127.0.0.1:4318 (`npm run dev:test`)
- 최초 준비: `npm run db:setup`, `npm run accounts:setup`, `node scripts/migrate-followups.mjs development`
- 서버 실행 후 달력 사례 추가: `npm run demo:calendar` (중복 생성하지 않음)
- 개발 계정표: `.local/development-accounts.md` (로컬 전용, 초기 발급 비밀번호)
- 테스트 준비: `npm run db:setup:test`, `node scripts/setup-accounts.mjs test`, `node scripts/migrate-followups.mjs test`

## 다른 장소에서 피드백 접속 (임시 공유)

`npm run dev` 실행 상태에서 `npm run share:feedback`을 실행합니다. `.local/tools/cloudflared`가 필요하며 현재 macOS arm64 공식 2026.10.0 바이너리를 SHA256 검증 후 프로젝트 내부에 설치했습니다. [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)로 임시 HTTPS 주소를 만들고, 비밀번호를 받는 별도 게이트웨이(127.0.0.1:4319)를 거쳐 기존 개발 서버(4317)로 연결합니다. 운영 서버나 운영 DB는 생성하지 않습니다.

- 주소·공유 비밀번호·종료 예정 시각: `.local/feedback/access.json` (개인 접근 권한 600). 실행할 때마다 주소와 공유 비밀번호가 새로 만들어집니다.
- 공유 비밀번호 입력 → 기존 브랜드/직원 계정 로그인 순서입니다. 공유 비밀번호는 신뢰하는 피드백 참여자에게만 전달합니다. 테스트 계정은 기존 비밀번호를 유지합니다.
- 8시간 뒤 자동 종료됩니다. 실행한 터미널에서 Ctrl+C로 즉시 종료할 수 있습니다. 컴퓨터 종료·잠자기·네트워크 끊김·개발 서버 종료 시 접속되지 않습니다. 기존 127.0.0.1 접속은 그대로 사용합니다.
- 같은 개발 DB를 사용하므로 참여자의 저장도 로컬 데이터에 반영됩니다. 운영용 상시 서비스가 아닙니다. 원격 화면은 수동 새로고침으로 최신 변경을 확인합니다.
- 모든 API/소스/파일 앞에서 공유 인증을 검사하고, 정확히 발급된 도메인과 쓰기 요청 Origin을 확인합니다. 인증 이후에도 `.local`, 환경 파일, 백업, 다른 프로젝트 경로를 차단합니다. 원래 CRM의 로컬 전용 guard는 변경하지 않습니다. 게이트 쿠키는 Secure/HttpOnly/SameSite=Strict이며 기존 CRM 응답 쿠키에도 외부 HTTPS용 Secure를 추가합니다.
- 검증: `node --test tests/feedback-gateway.test.mjs`. 외부 주소에서도 미인증 API 차단, 개인 파일 차단, 잘못된 Origin 차단, 듀담 로그인과 자사 고객 20건 조회를 확인했습니다.

- 자료실: 브랜드·검색·필독 고정, PDF/PNG/JPG/WEBP 업로드(10MB), 인증된 미리보기·다운로드, 이전 파일 버전 보관과 새 버전 확인 초기화. 기본 자료 제목은 예시이며 실제 파일은 관리자 업로드 후 열립니다.
- 엑셀: 현재 검색/필터에 해당하는 허용 고객을 XLSX로 다운로드합니다. 본사 화면에는 다운로드 버튼을 제공하지 않습니다. 로그인 후 조회 가능한 데이터의 별도 복사를 막는 DRM 기능은 아닙니다.

### 고객 DB 분류·접수일시

- 창업 형태는 `신규창업 / 업종변경 / 샵인샵`이며, 비어 있거나 알 수 없는 값은 `미분류`로 표시합니다. 띄어쓰기 차이와 `숍인숍`, `Shop-in-Shop`은 `lib/lead-fields.ts`의 공통 함수로 정리합니다. 직접 등록·창업 조건 수정도 같은 기준을 사용하며 최초 문의 원문은 보존합니다.
- Google Sheets 연결 시 실제 시트의 창업 형태 열을 이 분류 함수에 연결하고, 원본 값은 `Inquiry.raw`에 보존해야 합니다. **현재 자동 수집은 연결하지 않았습니다.** 시트 접수일시는 가져온 시간이 아닌 원본 제출 시각을 `Inquiry.receivedAt`에 저장합니다.
- 목록의 접수일시는 가장 이른 문의 접수 시각을 한국시간으로 표시합니다. 문의가 없는 기존 자료만 CRM 등록 시각을 대신 사용하고, 날짜만 있는 자료의 시간은 `—`로 표시합니다. 재문의로 최초 접수일시가 바뀌지 않습니다.
- 목록은 기본 25개, 선택 시 50/100개씩 표시합니다. 창업 형태 필터와 엑셀 다운로드에도 같은 분류·접수일시를 적용했습니다.
- 분류·시간 검증: `node --experimental-strip-types tests/lead-fields.test.mjs`

### 지역·메타 원본 연락처·브랜드별 중복·진행상태 관리

- 고객 목록과 엑셀에 희망 지역을 표시합니다. 목록의 긴 지역명은 마우스를 올리면 전체를 볼 수 있습니다.
- 메타 문의 상세에는 `Inquiry.metaAutoPhone` 또는 원문 `메타 자동입력 연락처` / `메타 자동입력 전화번호` / `phone_number` 값을 별도로 표시합니다. 메타 유입에서만 사용하며 일반 `연락처`를 자동입력 번호라고 추정하지 않습니다. 값이 없으면 `미수집`입니다. Google Sheets 실제 연결 시 해당 원본 열을 별도로 매핑해야 하며, 기본 고객 연락처를 덮어쓰거나 이 번호로 고객을 자동 병합하지 않습니다.
- 중복 기준은 **브랜드 + 기본 고객 연락처**입니다. 다른 브랜드에서는 같은 연락처로 별도 등록·배정할 수 있습니다. 같은 브랜드의 재문의는 기존 고객에 추가합니다. 수집 경로는 공통 `normalizePhone`으로 국내/국가번호 형식을 정리해야 합니다. DB 고유 인덱스가 동일 브랜드의 동시 등록을 막습니다.
- 관리자는 `타 브랜드 문의` 필터와 상세보기에서 같은 기본 연락처를 가진 다른 브랜드의 고객·담당자를 확인할 수 있습니다. 이 UI는 관리자 전용이며, 직원·본사 API에는 기존 권한 밖의 고객/문의가 반환되지 않습니다.
- `관리자 설정 → 진행상태`에서 항목을 추가하거나 사용 중지/다시 사용할 수 있습니다. `부동산 임장중`이 기본 제공됩니다. 사용 중지된 상태의 기존 고객·상담 이력은 유지되며 새로운 변경에만 선택이 제한됩니다. 기존 기본 7개 상태는 상담·성과 연동 때문에 유지합니다. 사용자 추가 항목은 삭제/이름 변경 없이 보존합니다.
- `drizzle/0004_outstanding_ultron.sql`: 상태 설정 저장소와 브랜드별 연락처 고유 인덱스. Drizzle의 표현식 인덱스 SQL 출력 오류를 미적용 단계에서 수정하고, SQLite와 로컬 개발/테스트 DB에서 적용을 검증했습니다. 재생성 시 표현식을 컬럼명으로 인용하지 않도록 SQL 검토가 필요합니다.
- 검증: `python3 tests/intake-status-smoke.py`는 격리된 4318 테스트 서버만 사용해 브랜드 간 동일 고객의 별도 배정, 권한 격리, 동시 중복 등록, 메타 원본 번호 분리, 상태 추가·중지·복원·이력 보존을 확인합니다.

### 성과 그래프

통화·미팅 횟수 추이 대신 **접수 고객의 현재 결과**를 보여줍니다. 기본 조회는 이번 달이며, 최초 문의 접수일(한국시간)이 선택 기간에 포함되는 고객을 집계합니다. 문의가 없는 기존 고객만 CRM 등록일을 대신 사용합니다. 같은 브랜드의 재문의는 새 고객으로 세지 않으며 다른 브랜드에 별도 등록된 문의는 각 브랜드의 고객으로 집계합니다.

- 접수 고객 / 진행 중 / 계약 완료(접수 대비 비율) / 보류·종료를 상단에 표시합니다. 계약 비율은 현재 계약 완료 상태인 고객 ÷ 기간 내 접수 고객입니다. 과거 조회 종료일 당시 상태를 복원하는 지표가 아니며 현재 상태가 바뀌면 결과도 바뀝니다.
- 진행상태 막대는 같은 접수 고객 집단의 현재 상태 분포입니다. 누적 퍼널로 추정하지 않습니다. 사용자 추가·사용 중지된 상태도 실제 고객이 있으면 포함합니다.
- 관리자 ‘담당자별 계약’은 현재 담당자별 계약 완료/접수 고객 수와 비율을 함께 표시합니다. 재배정 시 현재 담당자에 반영되며 실적 귀속이나 순위를 의미하지 않습니다. 본사는 허용된 브랜드의 계약 비율만 표시합니다.
- ‘지금 확인할 고객’은 접수 기간과 무관한 현재 보유 고객 기준입니다. 계약 완료·종료를 제외하고 보류는 포함합니다. 관리자 미배정, 배정 고객의 접촉 기록 없음, 연락 지연, 연락 기록은 있으나 다음 약속 없음으로 구분합니다. 접촉 기록 없음은 통화 완료/부재/번호 오류 기록이 없다는 뜻이며 기존 메모만 있는 고객도 포함합니다. 항목 간 중복될 수 있습니다. 본사에는 내부 관리 지표를 만들거나 표시하지 않습니다.
- 막대와 숫자를 누르면 해당 고객 목록으로 이동합니다. 접수 고객이 0명이면 비율은 `—`로 표시하며 기존 연락 지연 등 현재 업무는 유지합니다. 고객 DB 화면의 담당자 필터가 성과의 별도 담당자 필터와 숨겨진 교집합을 만들지 않도록 분리했습니다.
- 기존 통화·미팅·배정 표는 ‘기간 내 활동 기록 상세’에 보존했습니다. 이 표는 활동 발생일 기준이므로 위 접수 집단 그래프와 집계 기준이 다릅니다.

검증: `node --experimental-strip-types tests/performance-chart-data.test.mjs`는 최초 접수/재문의, 한국시간 경계, 상태 합계와 분모, 오래된 고객의 미처리 업무, 중복 제외, 권한 범위, 본사 내부 지표 차단, 빈 기간을 확인합니다. Chrome에서 브랜드·담당자 필터, 계약 그래프의 고객 목록 이동, 접수 없는 기간에도 기존 연락 지연 유지 동작을 확인했습니다. 타입·린트·개발 빌드 통과. 기존 로컬 데이터와 운영 분리 설정을 변경하지 않았습니다.

### 통화 중심 고객 상세 팝업

고객 상세를 중앙의 큰 팝업으로 구성했습니다. 상단에는 고객·브랜드·담당자·연락처, 왼쪽에는 고객 요약/상담 이력, 오른쪽에는 상담 입력을 배치합니다. 왼쪽 참고 자료를 스크롤하거나 이력 탭으로 전환해도 오른쪽 입력은 유지됩니다. 좁은 화면은 상하 배치로 전환하며 저장 버튼은 하단에 고정합니다.

입력 순서는 메모 → 통화 결과 → 다음 행동 → 저장입니다. 부재·연락처 오류는 메모 없이 결과만 저장할 수 있습니다. 재연락은 1시간 뒤/내일 오전 10시 단축 선택을 제공하고, 미팅은 시작·종료·장소·제목을 같은 폼에서 작성합니다. 미팅 저장 시 기존 재연락은 완료 처리하고 진행상태는 미팅 예정으로 설정합니다. 예정 미팅은 고객 요약에서 바로 열 수 있습니다. 메모만 저장하면 약속과 상태를 유지합니다.

초안은 기존 계정·환경·고객별 sessionStorage를 사용합니다. 팝업 닫기/재열기, 이력 열람, 창업조건 보조 창을 사용해도 초안을 유지합니다. 서버에 저장한 상담 이력과 구분하며 브라우저 탭 종료 후 초안 보존은 보장하지 않습니다. 본사는 요청 작성만 제공하며 내부 재연락과 상담 결과 입력은 노출하지 않습니다.

### 마지막 수정일과 DB 사랑방

- 고객 목록·상세·엑셀에 마지막 수정일을 표시합니다. 성과 화면의 조회 기준을 최초 접수일/마지막 수정일 중에서 선택할 수 있습니다. 마지막 수정일 조회도 해당 고객의 현재 상태를 보여주며 과거 상태 복원이나 모든 변경 건수 집계가 아닙니다.
- `leads.updated_at`은 DB 트리거로 기록합니다. 고객 내용·진행상태·담당자 변경, 상담/메모/본사 요청 저장, 추가 문의 접수, 미팅/재연락 등록·변경 시 갱신합니다. 조회, 문의 확인, 알림 확인, 자료 열람은 갱신하지 않습니다. 새 날짜는 클라이언트가 지정하지 못합니다. 기존 데이터는 남아 있는 접수·상담·활동·일정 변경 이력에서 가장 늦은 시각을 계산하며 미래 예약 일시 자체는 수정일이 아닙니다.
- DB 사랑방은 서버 시각으로 마지막 수정 후 **480시간(20일)** 경과한 배정 고객을 표시합니다. 계약 완료·종료, 앞으로의 예정 재연락·미팅이 있는 고객은 제외합니다. 미배정은 기존 관리자 배정 화면을 사용합니다. 영업사원은 자신에게 허용된 브랜드 중 다른 담당자의 고객만 볼 수 있고 본사 계정에는 메뉴와 데이터가 제공되지 않습니다.
- 인수 전에는 브랜드·고객명·지역·창업형태·진행상태·기존 담당자·수정일만 반환합니다. 연락처·문의 원문·상담 내역은 반환하지 않습니다. ‘내가 재컨택하기’로 인수한 뒤 기존 상세보기에서 확인합니다. 관리자는 목록 확인과 고객 보기만 제공하며 영업사원 계정으로 인수합니다.
- 인수는 DB 조건부 갱신과 하나의 batch로 처리합니다. 서버가 20일·브랜드·현재 담당자·예정 약속을 다시 검사하며 선착순 한 명만 성공합니다. 인수 직후 수정일을 갱신하고 기존 상담 이력을 보존하며 남아 있는 미처리 재연락/과거 미팅도 새 담당자로 넘깁니다. 이전 담당자는 이후 해당 고객의 조회/수정을 할 수 없습니다. 영업사원의 상담·상태·조건·일정·재문의 저장에는 같은 트랜잭션 내 소유권 확인을 추가해 인수 전에 열린 화면의 늦은 저장도 막습니다.

### 광고대행 고객사의 직접 CRM 운영 (2026-10-13)

- 일반 광고대행 계정은 `client_admin`: 자기 브랜드의 전체 고객 DB, 배정, 상담, 미팅·재연락, 성과, 직원·계정 관리. 첫 화면은 고객 DB입니다.
- `직원·계정 관리 → 직원 추가`에서 이름·아이디·초기 비밀번호·담당 브랜드를 한 번에 저장합니다. `client_staff` 직원은 자기 담당 브랜드의 배정 고객만 관리합니다. 직접 접수한 고객은 본인에게 배정됩니다.
- 기존 `client` 영업대행 계정은 조회·요청만 가능합니다. 모든 외부 계정에서 내부 업체 관리 홈·자료실·DB 사랑방을 숨기고 관련 데이터를 서버에서 제외합니다. 회사별 직원 캘린더는 해당 고객사 관리자만 조회합니다.
- 소속은 `Member.tenantId`에 고객사 관리자 계정 ID로 저장합니다. 고객사 요청에 포함된 소속·역할·임의 직원 연결은 거절합니다. 직원 계정과 회원 정보는 한 트랜잭션으로 생성·수정합니다. 최고관리자만 고객사 관리자 권한을 발급하며, 같은 브랜드의 고객사 관리자 중복 발급은 차단합니다.
- 고객사 관리자가 복수의 광고대행 브랜드를 보유하면 직원별 담당 브랜드를 선택할 수 있습니다. 영업대행이 포함된 브랜드에는 직접 운영 권한을 부여하지 않습니다. 상위 고객사 계정 비활성화·권한/브랜드 변경은 직원의 다음 요청부터 반영됩니다.
- 다른 고객사의 계정·직원·고객은 조회/수정/배정할 수 없습니다. 직원 재배정 시 상담 이력은 유지되고 예정 미팅·재연락은 새 담당자에게 인계됩니다. 이전 직원은 즉시 접근할 수 없습니다. 우리 회사의 기존 내부 메모는 고객사에 공개하지 않으며, 고객사가 작성한 내부 메모는 자기 회사 내에서만 확인합니다.
- 개발 데이터의 8개 광고대행 브랜드 계정만 직접 관리 권한으로 전환했습니다. 기존 아이디·비밀번호 및 고객/상담/일정 데이터는 유지합니다. `scripts/enable-company-crm-local.py development|test`는 이 전환만 수행하고 이력 불변을 검사합니다.
